# Scientific methodology and conclusions (implementation-aligned)

## Main research question
How do executed-workflow topology, retries, resource demand, ingress placement, and synthetic network constraints affect cost-minimizing edge/cloud placement and routing?

## Traceable pipeline
Generic BT -> execution trace -> executed-path BT -> unchanged SWI-Prolog BT-to-Service-Graph -> resource model -> SciPy HiGHS independent MILP -> independent feasibility audit -> optional Neo4j Cypher export.

The fixed BT can reach Strategy A, Strategy B, or Recovery. Failed service actions that actually ran remain present in the SG. A failed retry attempt consumes synthetic operation work; repeated attempts do not automatically imply simultaneous CPU replicas.

## Model assumptions
- Requests per second determine offered computation and link traffic, not the 1000 Monte Carlo replications.
- Synthetic CPU throughput (operations per vCPU second), memory by workload class, synthetic message sizes, headroom and arrival rate are recorded in `config/research_scenario_strict.json`.
- The original professor network resources, capacity blocks and cost coefficients are preserved exactly. Costs are mixed model reference units, not monetary euros.
- CPU demand = max(minimum floor, work units/request * request rate / reference ops/s/vCPU * headroom).
- Bandwidth uses labeled data edges only; pure control dependencies do not create separate traffic.
- Capacity Stress is a **scenario overlay** (600 blocks Core and 5x request rate), not an edit to the professor's network.
- The actual HiGHS MILP `solver_relative_gap` comes from the scenario config; independent audit recalculates objective and capacities.

## Six ablations
| Scenario | Pin F1=edge1 | Synthetic 2 ms per physical link | Bound 4 ms per data dependency | Core cap 600 blocks; 5x offered rate |
|---|---|---|---|---|
| baseline | no | no | no | no |
| ingress_only | yes | no | no | no |
| latency_only | no | yes | yes | no |
| latency_path | yes | yes | yes | no |
| capacity_stress | no | no | no | yes |
| combined | yes | yes | yes | yes |

**Important**: The delay bound applies to each selected service dependency separately, not the complete workflow. No request latency SLA, link serialization delay, queuing or processing time is constrained. Thus latency_only can produce the same optimum as baseline. Do **not** report that latency is universally irrelevant or force edge selection.

## Audit scope
Audits require that every service be placed on a legal site, every labeled data dependency have exactly one valid route, every hop be physical and contiguous, CPU/RAM and link capacities not be exceeded, site/connection block rounding valid, pinned placements honored, per-data-edge delay limit honored, and model objective match recomputation. Passing checks validates the implemented constraints, not the assumptions or global equivalence to the professor's PuLP optimizer.

## What has been observed (user-run experiments, Oct 2026; NOT reproduced within this ZIP)
- Seeds 42, 123, 2026: 1000 executions each; 7 SG topology families; 17 unique topology+workload signatures per seed.
- Each seed: 102 cases (17 groups * 6 scenarios), each independently audited PASS, 306/306 across seeds.
- Strategy A/B/Recovery counts per seed: 42: 547/311/142; 123: 532/357/111; 2026: 540/332/128.
- Average synthetic operations per execution: 123556, 119930, 122404 respectively.
- Recheck outputs generated by this bundle independently; these numbers are observations from the user's earlier Terminal logs, not embedded empirical measurements.

## Do not overclaim
- Synthetic resources are neither lab measurements nor Fastweb/Vodafone datasets.
- Only 3 seeds: descriptive replication, no strong statistical inference.
- No independent global optimality certificate beyond solver's status/bounds and MILP gap; an audit validates feasibility, not optimality proof.
- No actual deployment; generated Neo4j Cypher is not proof that data was loaded into Neo4j.
- No calibrated queuing, CPU parallelism, user-to-access RTT, E2E SLA, physical access-path anchoring, or time-resolved multi-request network load.
- Network graph original CPU/RAM block ratio is artificial. Include sensitivity analysis of hardware block specification before attributing observed changes to workload.
